🧑‍🤝‍🧑 Pruebas de concurrencia

Experimento aparte, no comparable al resto del informe: mismo menú, cantidad creciente de usuarios navegando en simultáneo, para ver cómo se degrada el tiempo de respuesta bajo carga.

📖 Cómo leer esta pestaña

Corrida = una ejecución completa del escenario a un nivel de concurrencia dado (lo que en testing de carga se conoce como un test run). Muestra = un tiempo individual dentro de esa corrida, uno por cada usuario simultáneo.

Ejemplo: si la fila de "5 usuarios" muestra Corridas=3 y Muestras=15, significa que ese escenario (5 usuarios navegando al mismo tiempo) se corrió 3 veces en momentos distintos, y cada corrida aportó 5 tiempos (5 × 3 = 15) — el P95 de esa fila se calcula sobre esas 15 muestras juntas, no sobre una sola corrida.

En el gráfico, el eje X es la cantidad de usuarios concurrentes y el eje Y el P95 (en segundos) de todas las muestras acumuladas en ese nivel. Una curva que sube de a poco es esperable; un salto brusco entre dos niveles marca el punto donde el sistema empieza a degradarse bajo carga. La columna Δ vs 1 usuario compara cada nivel contra el nivel base de 1 usuario: negativo = más lento con más usuarios (degradación), positivo sería una mejora — inusual en este tipo de prueba. Con Corridas=1 (marcado con ⚠️ en la tabla), tratá ese nivel como orientativo: todavía no es un P95 estadísticamente confiable, es la medición de una sola ejecución.

Sincronización entre usuarios: el workflow de GitHub Actions está preparado para que los N usuarios arranquen el test casi al mismo segundo, pero hay distintas cuestiones previas (compilación del spec, apertura del navegador, etc.) que varían unos segundos entre ejecuciones, así que ningún usuario llega a ejecutar la misma acción en el instante exacto. Aun así, se solapan de forma real y sostenida durante la mayor parte de la corrida (~70-80% del tiempo total en las pruebas de validación realizadas) — es carga concurrente genuina sobre el servidor, no una corrida secuencial disfrazada.
